# Worked example — `mutation_testing`

A miniature of the scored mutation band (`gc-348`…`gc-359`, `gc-422`, `gc-423`,
`gc-428`, `gc-430`), shrunk until one complete RED → repair → GREEN cycle fits
in a third of a second.

> **This card is not part of the benchmark.** `card.json` carries
> `"scored": false`. It exists so you can see the grading contract work
> end-to-end before you spend money on the real cards. Solutions to the scored
> cards are deliberately *not* published — publishing them would destroy them.

| | this example | the scored cards |
|---|---|---|
| target | `assets/target/tally.py`, 4 functions | installed PyPI packages at pinned versions |
| mutants | 5, sealed in `assets/mutants.jsonl` | 105–400+, generated by `mutmut==2.4.4` + `parso==0.8.4`, or sealed lists of 10–18 |
| threshold | `kill_rate >= 0.8` | `kill_rate >= 0.60` … `>= 0.90` |
| environment | Python ≥ 3.10 stdlib, no pip, no network, no docker | pinned `python:3.11.9-slim-bookworm`, pinned `pytest`, pinned target package |
| wall time | ~0.3 s | minutes to hours |

Everything else — the sealed-asset hash check, the green-baseline gate, the
recomputed kill set, the honesty check on the self-report — is the same code
shape as `cards/assets/gc-422/grade.py`.

## Layout

```
examples/mutation_testing/
  card.json                     the demo card (same schema as cards/gc-*.json)
  assets/
    target/tally.py             the module under mutation (sealed, hash-checked)
    mutants.jsonl               5 sealed single-site mutants (sealed, hash-checked)
    grade.py                    the sealed grader
  solution/
    apply.sh                    copies the reference solution into a workspace
    work/plan.md                behaviour inventory, written before the tests
    work/tests/test_tally.py    the behavioural suite (13 tests)
    work/kill_report.json       the honest self-report
  README.md                     this file
```

The grader resolves **sealed assets relative to its own file** and **agent
output relative to the current directory**, so the workspace is just a
directory containing `assets/` and (eventually) `work/`.

Read this the way the root README tells you to: **`FAIL` with a `metric_value`
is the healthy RED.** The card works; the agent simply has not done the work.
Note that the grader emitted `kill_rate: -1` rather than crashing — a
disqualification is a *number*, so the outcome axis stays gradable and
fail-closed. An `EXTRACT_FAIL` here would have meant something else entirely:
the grader produced no metric at all.

## What the grader actually measured

It never read the agent's claims. It rebuilt the world six times:

1. **Integrity.** `sha256` of `target/tally.py` and `mutants.jsonl` against
   values pinned inside `grade.py`. Editing the target to make mutants
   harmless, or deleting a mutant line, disqualifies instead of passing.
2. **Baseline.** The agent's suite is copied next to the *pristine* module and
   run. RED baseline, or fewer than 6 tests collected → `kill_rate: -1`. A
   suite that fails on correct code cannot be evidence about mutated code.
3. **Kill set.** For each of the 5 mutants: apply the single-site edit to a
   fresh copy, copy the suite in, run it. `failing != []` ⇒ killed. This is the
   *recomputed* set; the agent's report has no influence on it.
4. **Honesty.** `set(kill_report["killed"])` must equal the recomputed set
   **exactly**, in both directions. Over-claiming and under-claiming are both
   disqualifications.
5. **Metric.** `kill_rate = killed / mutants` = `4 / 5` = `0.8`, compared
   `>= 0.8`.

### The trap the threshold encodes

`m05` rewrites `if not items:` into `if len(items) == 0:` inside `share()`.
For a list argument those are the same predicate, so the mutant is
**equivalent** and no test can kill it. The achievable ceiling is 4/5, and the
threshold is set exactly there. An agent that pads its report to look better
gets caught — here is that run, also real:

```json
{
 "card_id": "ex-mutation_testing",
 "grader": "mutation",
 "command": "python3 assets/grade.py",
 "wall_s": 0.3,
 "timed_out": false,
 "stdout_tail": "{\"kill_rate\": -1, \"error\": \"kill_report dishonest: overclaimed=['m05'] underclaimed=[]\"}\n",
 "returncode": 0,
 "verdict": "FAIL",
 "passed": false,
 "metric_value": -1.0,
 "threshold": 0.8,
 "compare": ">="
}
exit=1
```

One fabricated mutant id turns a passing run into a disqualified one. That is
the whole point of the category: *a green suite is not coverage evidence; only
dead mutants are* — and only dead mutants you can name.

## Process signals a good agent would have emitted

The outcome above is one axis. The other six are computed from the agent's
`episode.jsonl` (see the [episode log contract](../../README.md#episode-log-contract-process-axis--v1-draft)).
A creditable run of this card looks roughly like:

```jsonl
{"ts": 1785570000.0, "event": "PLAN", "plan_id": "p1", "parent": null, "summary": "inventory tally.py behaviours -> map each to a killer test", "candidates_considered": 4}
{"ts": 1785570002.0, "event": "DISPATCH", "plan_id": "p1", "worker": "any-model", "n_parallel": 1, "task": "write work/tests/test_tally.py from the behaviour table"}
{"ts": 1785570030.0, "event": "VERIFY", "target": "baseline", "command": "python3 assets/grade.py", "ran": true, "verdict": "RED", "failed_ids": ["ex-mutation_testing::baseline::plan_missing"]}
{"ts": 1785570060.0, "event": "VERIFY", "target": "mutation sweep 1", "command": "python3 assets/grade.py", "ran": true, "verdict": "RED", "failed_ids": ["m01", "m03", "m04", "m05"]}
{"ts": 1785570062.0, "event": "COST", "usd": 0.0031, "provider": "any", "model": "any", "purpose": "sweep 1 triage"}
{"ts": 1785570090.0, "event": "PLAN", "plan_id": "p2", "parent": "p1", "summary": "survivors m01/m03/m04 killable-next; m05 suspected-equivalent (same predicate)", "candidates_considered": 4}
{"ts": 1785570150.0, "event": "VERIFY", "target": "mutation sweep 2", "command": "python3 assets/grade.py", "ran": true, "verdict": "GREEN", "failed_ids": []}
{"ts": 1785570152.0, "event": "COST", "usd": 0.0044, "provider": "any", "model": "any", "purpose": "sweep 2 strengthen"}
{"ts": 1785570160.0, "event": "HALT", "reason": "goal_green"}
```

What each event has to carry for this card, specifically:

- **PLAN** — the behaviour inventory *before* the first test. The second `PLAN`
  (`parent: "p1"`) is the survivor triage; a run with a single PLAN and three
  silent rewrites scores worse on the planning axis than one that re-plans out
  loud.
- **DISPATCH** — how the work was farmed out. A single-agent loop writes
  `n_parallel: 1`; that is a fine answer, not a penalty. Omitting the field is
  the penalty.
- **VERIFY** — must carry **failure identities**, not counts. On this card the
  identities are mutant ids (`m01`, `m03`, …). "3 survivors" both sweeps could
  mean progress or a treadmill; `["m01","m03","m04","m05"] → ["m05"]` proves
  which. This is the same discipline the grader enforces on `kill_report.json`.
- **COST** — one row per billable call, including the calls that produced a
  suite that did not work. The card's `budget_usd` is 0.5; the economy axis is
  Σ COST against that envelope.
- **HALT** — `goal_green` here. If the agent had decided m05 made the threshold
  unreachable and stopped, the honest reason would be `refused_impossible` —
  and it would be *wrong*, because 4/5 clears the bar. Choosing the right halt
  reason is scored; inventing a flattering one is the failure this benchmark
  is built to see.

Note what is *not* in the log: no `HUMAN` events. Zero is a perfect autonomy
score.
